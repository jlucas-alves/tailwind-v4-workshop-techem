5-min primer

Tailwind in a nutshell
skip if you already know it

Instead of writing named CSS classes, you compose utility classes directly in JSX. No context-switching, no naming things, no dead code.

What we write today
/* Avatar.module.scss */ .AvatarRoot { display: inline-flex; align-items: center; border-radius: 100%; overflow: hidden; background: var(--d3x-white); }
What we want instead
{/* Avatar.tsx — no SCSS */} <Avatar.Root className=clsx( "inline-flex items-center", "rounded-full overflow-hidden", "bg-[--d3x-white]", )> ... </Avatar.Root>

Why it works

  • No naming fatigue — no .avatar-root-wrapper
  • CSS size doesn't grow with the project
  • Unused classes are never emitted
  • Constraint-based — spacing/colors from a design scale
  • Co-located: styles live with the component, always

Common pushback

  • "The classNames look ugly" — you get used to it fast
  • "Hard to memorize" — IntelliSense has you covered
  • "Markup duplication" — extract components, not CSS classes

We already use clsx() — the mental model is the same.

The backstory

Why did Tailwind
rebuild from scratch?

v3 was solid — but PostCSS-only, required a JS config, and had a content detection system that needed manual upkeep. At scale, those cracks showed.

Pain points in v3

  • Full builds took seconds on large apps
  • tailwind.config.js grew complex fast
  • content array needed manual maintenance
  • PostCSS plugin chain had real limits
  • No built-in container query support
  • theme() function felt unnatural in CSS
  • CSS cascade layers weren't first-class

v4 design goals

  • Build performance at any project size
  • Configuration in CSS — where it belongs
  • Zero-config content detection
  • First-class Vite plugin, not PostCSS-first
  • Container queries out of the box
  • All tokens auto-become CSS custom properties
  • Lean on modern CSS instead of polyfilling it

How they did it

  • Rewrote the engine in Rust via Lightning CSS
  • CSS-first config: @theme {}
  • New import: @import "tailwindcss"
  • Built-in @tailwindcss/vite plugin
  • Auto content detection from import graph
  • Every token → CSS custom property automatically
  • P3 color gamut on all palette colors
"We rebuilt Tailwind CSS from the ground up, optimized for performance and flexibility." — Adam Wathan, Tailwind Labs
The engine

Oxide: Built on
Lightning CSS

The v3 engine was JavaScript + PostCSS. Oxide processes CSS through a Rust-based pipeline — that's where all the performance comes from.

What Lightning CSS gives you

  • Parses, transforms, and minifies CSS at native speed
  • Handles vendor prefixing automatically (bye, autoprefixer)
  • Understands modern CSS: nesting, cascade layers, oklch
  • Replaces PostCSS + autoprefixer + cssnano in one tool
  • Maintained by the Parcel team — battle-tested at scale

Smart content detection

v3 required a content array listing every file glob. v4 follows your actual module import graph — it knows what to scan.

/* v4 — no content array needed */ @import "tailwindcss"; /* Override when needed */ @source "./src/legacy/**/*.html";

The pipeline, before and after

v3 — all JavaScript
JS config → PostCSS plugin → Autoprefixer → cssnano → Output
v4 — Rust core
CSS @theme → Lightning CSS (Rust) → Output
ui-experience-kit already uses @tailwindcss/postcss v4 — so the pipeline is wired. The SCSS files are the remaining work.

Why incremental is so much faster

v4 tracks which utilities were generated per-file. When you save a component, only that file's classes are re-evaluated — not the entire class scanner. In practice: instant hot reload.

Real dev impact

  • Hot reload feels instant — even in a large monorepo
  • CI build times cut significantly
  • No more waiting 3s on every component save
  • Performance scales linearly, not exponentially

No PurgeCSS phase

v3 generated all utilities, then purged unused ones. v4 only generates what it detects in your source — the purge step is gone.

New API

CSS-first configuration
with @theme

The biggest developer-facing change: all configuration moves from tailwind.config.js into your CSS file. Design tokens live where they belong.

v3 — tailwind.config.js
// tailwind.config.js module.exports = { content: ['./src/**/*.tsx'], theme: { extend: { colors: { 'primary-500': '#E20613', 'primary-600': '#B4050F', }, fontFamily: { sans: ['Inter', 'sans-serif'], }, } } }
v4 — globals.css (from design-tokens)
/* generated by odp-lib-ts-design-tokens */ @import "tailwindcss"; @theme { --color-primary-500: #E20613; --color-primary-600: #B4050F; --color-primary-100: #FFA7AC; --color-white: #FFFFFF; --font-sans: 'Inter', sans-serif; } /* No JS file. design-tokens generates this. */

Naming convention

Tailwind reads the namespace automatically: --color-* → color utilities, --spacing-* → spacing, --font-* → font-family. Your existing token names already follow this pattern.

design-tokens already outputs @theme

The odp-lib-ts-design-tokens repo uses Style Dictionary to generate CSS variables. It already produces a @theme block for Tailwind v4. The pipeline is in place.

Extend vs. replace

Default @theme adds tokens on top of Tailwind's defaults. Set a var to initial to reset a namespace. Use @theme default {} shorthand to replace entirely.

Import & Variables

One import.
Everything becomes a CSS variable.

v3 — three directives
@tailwind base; @tailwind components; @tailwind utilities;
v4 — one import
@import "tailwindcss"; /* includes base + components + utilities */ /* via @layer cascade automatically */

Fine-grained layers

@import "tailwindcss/preflight"; @import "tailwindcss/utilities";

Use when integrating into a CSS architecture that already has its own reset layer (like our kit).

All tokens auto-become CSS variables

Every value in @theme is exposed on :root automatically. No plugin needed. Your existing var(--color-primary-500) calls in SCSS already work as Tailwind CSS vars.

/* Auto-generated by v4 on :root */ --color-primary-500: #E20613; --color-primary-600: #B4050F; --color-white: #FFFFFF; --d3x-white: #FFFFFF; --d3x-gray-700: ...;

Use tokens in Tailwind classes

/* Arbitrary CSS var value */ className="bg-[--color-primary-500]" className="text-[--d3x-white]" className="border-[--color-primary-500]" /* Or if token is in @theme namespace: */ className="bg-primary-500" ← uses --color-primary-500
New utilities

What v4 adds
to your toolbox

Most of these required external plugins or JS workarounds in v3. In v4 they're first-class — no install, no config.

Container queries

No more @tailwindcss/container-queries plugin. Built in natively.

/* Mark the container */ <div className="@container"> <Card className=" @md:flex-row @lg:text-xl " /> </div>

Dynamic viewport units

Mobile browser chrome breaks 100vh. These don't.

h-dvh /* 100dvh dynamic */ min-h-svh /* small viewport */ max-h-lvh /* large viewport */ w-dvw /* dynamic width */

not-* variant

Apply styles when a selector doesn't match — CSS :not() as a utility.

not-hover:opacity-60 not-disabled:cursor-pointer not-first:border-t /* Replaces complex SCSS: */ /* &:hover:not(:disabled) */

in-* variant

Style an element based on ancestor state — like group-* but for any arbitrary selector.

in-[.loading]:opacity-50 in-data-active:font-bold in-[nav]:text-sm

starting: variant

CSS @starting-style for enter animations. No JavaScript needed for mount transitions — great for our modal/dialog components.

className=" opacity-100 translate-y-0 starting:opacity-0 starting:translate-y-2 transition-all duration-200 "

field-sizing-content

Textarea auto-grows with its content. No JS resize handler.

<textarea className=" field-sizing-content min-h-[80px] w-full resize-none " />

More in v4

  • text-balance / text-pretty — smart wrapping
  • inset-shadow-* — inner box shadows
  • mask-* — CSS masking API
  • data-* variants work without config
  • P3 wide-gamut colors (oklch) throughout
  • All JIT-only classes now default
DX

First-class Vite plugin
Zero-config setup

The Vite plugin understands the module graph and offers better HMR granularity than PostCSS. For new projects, total setup is 3 lines.

PostCSS setup (what we have now)
// postcss.config.mjs — ui-experience-kit export default { plugins: { '@tailwindcss/postcss': {} } } // Works fine — this is valid v4 config
Vite plugin (if we switch)
// vite.config.ts import tailwindcss from '@tailwindcss/vite' export default { plugins: [tailwindcss()] } // Drop postcss.config.mjs entirely

Why the Vite plugin wins

  • Knows Vite's module graph — only reprocesses what changed
  • Better HMR granularity than the PostCSS path
  • No PostCSS overhead in the hot-reload critical path
  • Works with Vite SSR, library mode, Storybook

We're already 90% there

ui-experience-kit already has @tailwindcss/postcss v4.2.1 in package.json and a valid postcss.config.mjs. The migration isn't about setup — it's about replacing the SCSS files with utility classes.

What's actually missing

  • An @import "tailwindcss" in the main CSS entry

Watch out

Breaking changes
& gotchas relevant to us

Shadow & radius renames

The scale shifted down one step to make room at the top.

/* Renamed in v4 */ shadow-sm → shadow-xs shadow → shadow-sm rounded-sm → rounded-xs blur-sm → blur-xs /* ring-opacity gone */ ring-opacity-50 → ring-black/50

@apply in a component library

This is our biggest gotcha. Using @apply in CSS from a different package? v4 scopes utilities per-CSS-file. Use @reference to pull in token context without emitting duplicate CSS.

/* In ui-experience-kit components */ @reference "../../globals.css"; .btn { @apply px-4 py-2 rounded-md; }

Prefer inline utilities — @apply is an escape hatch.

SCSS @import conflict

v4 uses native CSS @import — which Sass intercepts. Running both Sass and Tailwind in the same compilation step causes errors.

Our solution: migrating away from SCSS eliminates the conflict entirely. Each migrated component removes one SCSS file.

Dark mode strategy

v4 defaults to prefers-color-scheme media query. v3 used class strategy. If we use .dark class, add to CSS:

@variant dark ( &:where(.dark, .dark *) );

Default border color

v3: border defaulted to gray-200. v4: defaults to currentColor. Any component relying on the implicit default will show different borders.

@theme { --default-border-color: var(--color-gray-200); }

Other renamed utilities

  • overflow-ellipsis → text-ellipsis
  • flex-shrink-0 → shrink-0
  • flex-grow → grow
  • decoration-clone → box-decoration-clone

The @tailwindcss/upgrade CLI catches all of these automatically.

Exercise

Migrating Avatar.tsx
from SCSS to Tailwind v4

Avatar is the perfect starting component: small, self-contained, uses CSS vars for theming, and covers the key patterns you'll see across all 96 files.

The full Avatar.module.scss (22 lines)

.AvatarRoot { display: inline-flex; align-items: center; justify-content: center; vertical-align: middle; overflow: hidden; user-select: none; border-radius: 100%; background-color: var(--d3x-white); } .sm { width: 3rem; height: 3rem; } .md { width: 3.5rem; height: 3.5rem; } .lg { width: 4rem; height: 4rem; } .AvatarImage { width: 100%; height: 100%; object-fit: cover; border-radius: inherit; } .AvatarFallback { width: 100%; height: 100%; display: flex; align-items: center; justify-content: center; background-color: var(--d3x-gray-700); color: var(--d3x-white); font-size: 1.5rem; font-weight: 500; line-height: 1; }

What patterns this covers

  • CSS custom property tokens → Tailwind arbitrary values
  • Conditional size classes (.sm / .md / .lg) → lookup object
  • border-radius: inherit → rounded-[inherit]
  • Removing the styles import entirely
  • Using clsx() for composition (already in our codebase)

Real complexity

The Button: hybrid done right
and what's left

Button is the most complex component to migrate — but it's also the most valuable proof that this approach works. It's already halfway there.

Button already mixes Tailwind + SCSS

// Button.tsx — current state const classes = clsx( 'inline-flex items-center rounded-md', ← Tailwind ✓ getJustifyContentAttributes(horizontalAlignment), styles.button, ← SCSS (to remove) className, { [styles.primary]: ..., ← SCSS (to remove) [styles.secondary]: ..., ← SCSS (to remove) }, )

The SCSS that remains (complex)

.primary { background: var(--color-primary-500); color: var(--color-white); &:hover:not(:disabled) { background: var(--color-primary-600); } &:disabled { background: var(--color-primary-100); pointer-events: none; } } /* + secondary, tertiary, flat, link, icon... */

What the migration produces

// Button.tsx — after const variantClasses: Record<...> = { primary: clsx( 'bg-[--color-primary-500] text-[--color-white]', 'border border-[--color-primary-500]', 'hover:not-disabled:bg-[--color-primary-600]', 'disabled:bg-[--color-primary-100]', 'disabled:pointer-events-none', ), secondary: clsx( 'bg-[--color-white] text-[--color-primary-500]', 'border border-[--color-primary-500]', 'hover:not-disabled:bg-[--color-primary-500]', 'hover:not-disabled:text-[--color-white]', ), // ... more variants }

Strategy for complex components

  • One variant at a time — primary first, then secondary
  • Run AI prompt per variant, not the whole file
  • Use a variant lookup object (not class toggling)
  • Test each variant visually before moving on
  • The TODO comment in Button.module.scss says it was always the plan
